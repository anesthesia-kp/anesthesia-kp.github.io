## ⛔ THE CALENDAR FEED CANNOT BE BUILT ON THIS INFRASTRUCTURE — found 26 Aug. HIS DECISION.

**§54a specifies a per-doctor SECRET-URL `.ics` SUBSCRIPTION with no sign-in** ("calendar apps
cannot log in"), contents being that doctor's shifts plus approved vacation. **A subscription
needs an HTTP endpoint that returns `text/calendar` and keeps returning a fresh answer.
GitHub Pages serves static files only.** So §54's "build it" cannot be executed as designed
without new infrastructure, and that is his call, not Claude's. The three real options:

1. **Firebase Cloud Functions** — an HTTPS function reads the token and returns the `.ics`.
   The only option that delivers what §54a describes.
   **⚠ CLAUDE WAS WRONG ABOUT THE COST AND CORRECTED IT THE SAME DAY (26 Aug), on the owner's
   challenge — *"firestore seems generally quite cheap"*, and he was right.** Checked against
   published pricing rather than recalled: **$0.03 per 100,000 document reads, with 50,000 reads
   free per day.** Even the naive shape — 35 doctors, hourly polling, ~120 day-documents read per
   poll — is ~100k reads/day, half of it inside the free tier, about **$0.50 a month**. Cost is
   NOT a reason to refuse this, and leading with it was a bad call.
   **THE TWO REAL COSTS, NEITHER OF WHICH IS MONEY:**
   · **A public endpoint with admin credentials on the project that runs the LIVE auction.** A
     function using the Admin SDK bypasses `firestore.rules` completely. Containable — see the
     recommendation below — but it is a genuinely new surface and §2/§92 make it his call.
   · **A deploy path he does not have.** Functions need the Firebase CLI and Node tooling; he
     pushes with GitHub Desktop and pastes rules into a console, and command-line developer
     tools are still not installed on his Mac (`xcode-select --install` is an open item).
2. **Static `.ics` files committed to the repo — REJECTED, and it should not be reconsidered.**
   `vacation-kp.github.io` and `schedule` are PUBLIC repos. This would publish named doctors'
   schedules at guessable-by-enumeration URLs, and they would be stale until the next push.
3. **A client-side "download my calendar" EXPORT** — buildable today, zero infrastructure, zero
   ongoing cost, no secret URL, no rules surface. **But it is a one-time file, not a
   subscription**, so it loses the thing IDEAS 1b called the whole point: *"updating
   automatically"*. Honest half-measure, not the feature.

**Nothing was built.** §0 rule 4 and §3 rule 1: this is ambiguous in a way the code cannot
settle, so it stopped and asked. **§54's design-and-build go does NOT authorise adding Cloud
Functions to the shared project** — that is a decision of a different kind.

**▶ CLAUDE'S RECOMMENDATION, given 26 Aug: *"i'm ok with some additional cost"*. NOT YET RULED.**

**Build it — but store the finished `.ics` TEXT in a per-doctor document, and let the function do
nothing but hand it over.** `dailysched/feeds/{token}` holds the rendered calendar; the endpoint
looks up the token and returns the string.

Why this shape rather than the obvious one:
· **The function never queries the schedule, so it cannot leak anything else.** It reads ONE
  document path and has no code that could range over `vacations/*` even by mistake. That turns
  the security objection from "trust the code" into "there is nothing there to get wrong" — which
  is the only version of this worth putting on the auction's project.
· **One read per poll instead of ~120**, which puts the whole feature inside the free tier
  permanently rather than merely cheaply.
· **~20 lines with no schedule logic.** When the data model moves — and it will, Stage 5 is not
  finished — the change lands on the WRITER inside the admin page, which is tested here, not on
  an endpoint deployed by other means.
· The writer costs one small write per affected doctor when a day changes. Writes are $0.09 per
  100,000, with 20,000 free per day.

**Build it NOW rather than at release, and keep §54's release gate SHUT.** While no doctor is
subscribed, a bug costs nothing; the week it is announced is the worst possible week to be
finding them. The token needs its own ruling: where it lives, and who may regenerate it.
