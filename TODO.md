### FB-2 · Reads tracker — **DECLINED by the owner, 19 Aug 2026 ("skip the tracker"). Kept only as a record — do not re-propose.**

**What is NOT possible.** The Firestore client SDK exposes no read counter. The authoritative
daily figure lives in Google's billing system, reachable only via Cloud Monitoring with server
credentials — which a static public page cannot hold. So an admin card showing the TRUE
"reads used today" cannot be built. Anything shipped here is an estimate and must be labelled
as one on screen.

**What IS cheaply possible.** Both pages already funnel every listener through a single
wrapper — `function onSnapshot(ref, next, error)` (staff ~line 770, admin ~line 1683). That is
a clean choke point: counting each delivered snapshot there gives an EXACT read count **for
that tab**, at zero Firestore cost. Two useful readouts follow:
1. **This tab, exact** — reads since load, and a per-minute rate.
2. **Fleet estimate** — derived from data the admin page already holds: today's change-log
   entry count (a good proxy for bid actions) × the verified 3–5 listened-documents-per-action
   multiplier × an assumed concurrency, with all three assumptions shown so the number is
   auditable rather than magic. Costs no extra reads or writes.

**Anti-pattern to refuse if it comes up:** a shared counter document that every client
increments per read. That adds a WRITE per read AND re-broadcasts the counter to every
listener, making the exact problem worse. Do not build it.

**Priority, stated plainly:** a tracker WARNS, it does not PREVENT. The plan change (FB-1)
prevents. The tracker's real value is if the project STAYS on the free plan — the console's
usage figures lag, so an in-page live estimate would flag a hot day before the wall is hit.
On pay-as-you-go most of that value disappears. Also note this is a NEW FEATURE on the live
admin page during an audit hold: it needs its own "go", its own suite and its own honesty
check like any other build.
